# Reference Planning

- Purpose: Prove that authoritative application evidence is the exact media intended for the exact provider payload location.
- Interface: `modules/reference-planning/index.ts`
- Errors: `modules/reference-planning/errors.ts`
- Acceptance: `modules/reference-planning/reference-planning.test.ts`

Reference Planning validates application-relative containment, authority reasons, declared and detected media kind, SHA-256, actual media properties, and locked JSON Pointer destinations. Hashing and inspection use the same byte snapshot. Built-in PNG inspection requires the complete eight-byte signature and an IHDR header. Built-in MP4 inspection requires a parsed top-level container, `moov`/`trak`/`mdia` hierarchy, exactly one video track, every dense `stsd` sample description and `stsc` selection, recognized video and audio codecs whose kind agrees with each track's declared handler, complete and mutually consistent timing/chunk/sample tables, chunk offsets inside non-empty `mdat` evidence, and safe dimensions and duration. Marker-shaped byte strings, unknown sampled tracks, later-description audio, and audio codecs relabeled under a non-audio handler are refused. It then requires FFmpeg 6 at `/usr/bin/ffmpeg` to decode the exact snapshot from standard input with only the `pipe` protocol allowed and parses framehash evidence for decoded dimensions, duration, and audio presence. Container metadata must agree with decoded truth. A missing decoder, timeout, malformed framehash, metadata disagreement, decode failure, zero-sample timing table, or malformed declared video/audio track is a typed inspection failure. When bytes have a built-in signature, an injected inspector cannot relabel their media type. An injected Media Inspector for another application format must prove its recognized kind and supported exact media type; both are frozen into the Reference Plan and carried unchanged to Generation. Unknown bytes and kind/type contradictions are refused. An image cannot satisfy a Seedance video requirement.

Production agents obtain application bytes through the Effect-valued `fileApplicationFiles(applicationRoot)` adapter. It accepts one absolute, real application repository root and only safe application-relative paths. Absolute, home-relative, drive-prefixed, traversal, backslash, null-bearing, missing, non-file, and symlinked paths fail before Generation. Each read opens the verified application root, confirms its device and inode, walks each parent with no-follow semantics, opens the final file through that descriptor chain, and closes every descriptor before returning. Replacing a checked parent with a symlink after adapter initialization is therefore refused rather than redirecting the read. Repeated adapter construction retains no filesystem handle. Authoritative references remain owned by the declared application repository.
