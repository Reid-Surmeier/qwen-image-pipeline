# Run Record

- Purpose: Own the immutable request, durable attempt reservation, hash-chained events, write-once evidence, and replay-derived view for one application Run.
- Interface: `modules/run-record/index.ts`
- Errors: `modules/run-record/errors.ts`
- Acceptance: `modules/run-record/run-record.test.ts`

Provider response and poll evidence must match the shared closed schema for the Run mode and exact provider stage before any bytes are persisted. Run Record obtains the shared sanitizer's descriptor-strict wrapper snapshot and byte copy, then uses only that snapshot for validation, trial replay, intent, and persistence. Unknown, accessor-backed, or statefully substituted fields fail closed, including diagnostic fields whose contents use an unrecognized encoding. The shared Provider Evidence Sanitizer also owns recursive credential and duplicate-key checks as defense-in-depth; Run Record owns the typed refusal and persistence decision.

Generated Qwen and completed Seedance output wrappers, byte bodies, dense output arrays, and cost receipts are likewise snapshotted once before validation or persistence. Replay applies the raw duplicate-key refusal to both provider responses and every Seedance poll receipt.

Before writing `provider-response.json`, Run Record validates the mode-specific document, proves a complete trial replay, and journals a pre-write intent containing its expected hash, length, media type, and completion identity. Reservation reload reconciles an interrupted write only when the orphaned bytes match that earlier durable intent; substituted or intent-free storage is refused, and recovery never issues a new Submission Permit.

Run Record is the only production writer of Run evidence. `reserve` creates one durable attempt from a Planned Run, `record` applies a legal write-once operation, `load` verifies and replays authority, `readEvidence` returns bytes only after their journal receipt and SHA-256 have replayed successfully, and `readDiagnostics` returns defensive copies of the verified immutable request and journal with their replay-derived view. Production callers acquire the filesystem adapter through the Effect-valued `fileRunRecordLayer` constructor, then provide the resulting Layer; the storage writer and its Context tag stay inside the module. The filesystem adapter commits each extension as a write-once event frame before atomically materializing `events.jsonl`, so replay can finish an interrupted append without erasing a concurrent winner. Replay revalidates generated-output paths, media types, SHA-256 values, uniqueness, and evidence bytes; idempotent evidence calls also rehash their supplied bodies. A submission permit exists only in memory after the first durable submission-may-have-started event. Its consumer lives in a module-private WeakMap, so structurally similar caller objects are rejected at runtime; a genuine handle carries the reserved request and payload SHA-256 values, refuses any mismatched binding or second use, and is never recreated by reload. Consuming the handle records only that authorization transition; it cannot execute a caller-supplied Effect or bypass Generation.

Reservation freezes the application-owned correction ceiling and replayed correction depth. A linked successor is accepted only from the exact chain head of a definitive pre-submit failure, only when the parent proves no submission began, and only when objective, references, model, Procedure, or paid parameters materially changed. Before creating the child, Run Record appends one exact successor reservation to the parent; a sibling request then fails, while an interrupted creation may retry only that same request identity. The child must retain the same application and ceiling. Exceeding the ceiling, fanning out siblings, or relabeling an unchanged request fails before reservation.

Classified failures have fixed policy rather than caller-selected spend, retry, outcome, or ownership. Run Record writes a canonical `failure.json` through a durable intent and receipt; the document binds the immutable request SHA-256, exact pre-classification event head, existing artifact hashes, and an opaque failure proof issued by the Assembly, Verification, or Video Verification invocation over those exact inputs. A hand-built class, reused proof for different hashes, or phase-only assertion is refused. After a durable submission marker, an ambiguous timeout, malformed response, or output-count symptom can establish only the narrower Run Record fact `submission_unreconciled`: paid work may have started, no trustworthy result has arrived, and the Run is Blocked, possibly spent, and reconciliation-only. The symptom is not promoted into a durable causal finding without provider evidence. Real Assembly and Verification failures are unknown and reconciliation-only. A post-submit persistence interruption remains a typed interruption over the existing possibly-spent Run rather than a caller-asserted durable failure, and multiple output files never prove repeated failures. Repetition is derived only from verified failures across linked Runs and is stopped by the inherited correction ceiling. Budget exhaustion is refused by Planning before reservation. An adapter refusal after the durable submission marker is definitive only when the same in-process unused Submission Permit proves `submission_not_started`; a fake, consumed, or reloaded permit cannot manufacture that fact. Only a definitive pre-submit failure can permit a distinct material linked correction. Machine classifications are Verified Candidate, Human Decision Required, Blocked, or Failed, and never include owner Approval.

After provider evidence, generated outputs may be persisted under `outputs/`. A Run opens a donor-choice checkpoint only after the complete reserved output count is present, and its dense, unique SHA-256 list must name that exact persisted set. Both the write seam and journal replay independently enforce this complete-set rule. It then records a human-selected SHA-256 from that checkpoint and writes the separately hashed assembled output and canonical `assembly-report.json`. The report must bind the baseline reference, owned region, Exact Copy set, selected donor, and output back to the immutable Run Request; relabeling the raw donor is refused. `CommitChecks` accepts the hash-locked baseline bytes, then independently recomputes the fixed `rgba-fidelity-v1` result from those bytes and the persisted donor and assembled output before writing a replay-verifiable `checks.json` receipt. Run Record does not call Generation, perform Assembly, or declare subjective Approval.

For Seedance, provider evidence is rejected before persistence when its raw JSON contains duplicate object keys, so parsing cannot discard an earlier secret-bearing value. The sanitized submission response must contain one canonical job identity. Every poll event must name that same identity and stores its own ordered response under `polls/`. A completed poll receipt must itself bind the complete ordered MP4 output set by application path, media type, and SHA-256, plus completed count and actual, estimated-only, or unknown cost state; any omission, contradiction, or other runtime cost state is refused before an evidence write. If execution stops after the write-once poll body or output bytes but before their event is appended, the next same-job poll first reconciles that durable receipt against the retry operation, fills only matching missing output evidence, and journals the first durable poll rather than trying to overwrite it. When that first durable receipt is pending and the provider has since completed, Run Record journals pending first and leaves completion for the next same-job poll; it never resubmits. Orphans from another job, impossible status progression, output set, count, or cost fail closed. `CommitVideoChecks` accepts only a canonical `seedance-media-v1` report whose unique outputs cover the exact persisted set and whose expected properties, counts, cost, and mandatory checks agree with the immutable Video Plan and replayed evidence. Journal replay independently parses the persisted MP4 hierarchy, requires exactly one video track, validates every dense sample description and chunk-map selection, mutually consistent sample tables, recognized codecs whose media kind agrees with each track's declared handler, and media-data offsets, then requires a complete FFmpeg 6 framehash decode. Dimensions, duration, and audio presence come from decoded evidence and must agree with container metadata before replay preserves the classification; ambiguous tracks, falsified metadata, unknown sampled tracks, and relabeled audio fail closed, and the Video Verification report is never trusted as the media oracle. Reload issues no Submission Permit and derives the same job identity, poll count, output receipts, cost state, and classification from the journal. Run Record does not submit or poll a provider, perform Assembly, or declare subjective Approval.
