# Run Record

- Purpose: Own the immutable request, durable attempt reservation, hash-chained events, write-once evidence, and replay-derived view for one application Run.
- Interface: `modules/run-record/index.ts`
- Errors: `modules/run-record/errors.ts`
- Acceptance: `modules/run-record/run-record.test.ts`

Run Record is the only production writer of Run evidence. `reserve` creates one durable attempt from a Planned Run, `record` applies a legal write-once operation, `load` verifies and replays authority, `readEvidence` returns bytes only after their journal receipt and SHA-256 have replayed successfully, and `readDiagnostics` returns defensive copies of the verified immutable request and journal with their replay-derived view. Production callers acquire the filesystem adapter through the Effect-valued `fileRunRecordLayer` constructor, then provide the resulting Layer; the storage writer and its Context tag stay inside the module. The filesystem adapter commits each extension as a write-once event frame before atomically materializing `events.jsonl`, so replay can finish an interrupted append without erasing a concurrent winner. Replay revalidates generated-output paths, media types, SHA-256 values, uniqueness, and evidence bytes; idempotent evidence calls also rehash their supplied bodies. A submission permit exists only in memory after the first durable submission-may-have-started event. Its consumer lives in a module-private WeakMap, so structurally similar caller objects are rejected at runtime; a genuine handle carries the reserved request and payload SHA-256 values, refuses any mismatched binding or second use, and is never recreated by reload. Consuming the handle records only that authorization transition; it cannot execute a caller-supplied Effect or bypass Generation.

After provider evidence, generated outputs may be persisted under `outputs/`. A Run opens a donor-choice checkpoint only after the complete reserved output count is present, and its dense, unique SHA-256 list must name that exact persisted set. Both the write seam and journal replay independently enforce this complete-set rule. It then records a human-selected SHA-256 from that checkpoint and writes the separately hashed assembled output and canonical `assembly-report.json`. The report must bind the baseline reference, owned region, Exact Copy set, selected donor, and output back to the immutable Run Request; relabeling the raw donor is refused. `CommitChecks` accepts the hash-locked baseline bytes, then independently recomputes the fixed `rgba-fidelity-v1` result from those bytes and the persisted donor and assembled output before writing a replay-verifiable `checks.json` receipt. Run Record does not call Generation, perform Assembly, or declare subjective Approval.

For Seedance, the sanitized submission response must contain one canonical job identity. Every poll event must name that same identity and stores its own ordered response under `polls/`. A completed poll receipt must itself bind the complete ordered MP4 output set by application path, media type, and SHA-256, plus completed count and actual, estimated-only, or unknown cost state; any omission, contradiction, or other runtime cost state is refused before an evidence write. If execution stops after the write-once poll body or output bytes but before their event is appended, the next same-job poll first reconciles that durable receipt against the retry operation, fills only matching missing output evidence, and journals the first durable poll rather than trying to overwrite it. When that first durable receipt is pending and the provider has since completed, Run Record journals pending first and leaves completion for the next same-job poll; it never resubmits. Orphans from another job, impossible status progression, output set, count, or cost fail closed. `CommitVideoChecks` accepts only a canonical `seedance-media-v1` report whose unique outputs cover the exact persisted set and whose expected properties, counts, cost, and mandatory checks agree with the immutable Video Plan and replayed evidence. Journal replay independently parses the persisted MP4 hierarchy, every dense sample description and chunk-map selection, mutually consistent sample tables, recognized codecs whose media kind agrees with each track's declared handler, media-data offsets, dimensions, duration, and audio presence, then requires a complete FFmpeg 6 decode before preserving that classification; unknown sampled tracks and relabeled audio fail closed, and the Video Verification report is never trusted as the media oracle. Reload issues no Submission Permit and derives the same job identity, poll count, output receipts, cost state, and classification from the journal. Run Record does not submit or poll a provider, perform Assembly, or declare subjective Approval.
